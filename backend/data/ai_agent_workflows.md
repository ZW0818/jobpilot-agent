# Agent 工作流与工程边界

## 工作流与自主 Agent 的选择
工作流由代码规定步骤和依赖，自主 Agent 可根据模型输出动态选择步骤。简历解析、岗位分类、评分与报告具有稳定输入输出，适合明确的工作流；开放式研究更需要动态决策。面试问题：什么时候不需要多 Agent？如何防止角色拆分后重复调用模型？
项目证据建议：画出状态流转，说明每个节点的输入、输出、失败行为及模型调用次数。

## 并行执行与条件路由
无依赖任务可并行执行，例如候选人画像与岗位方向识别；依赖画像的检索必须等待上游完成。条件路由可按岗位方向选择知识库，在评估发现能力缺口后补充一次检索。面试问题：哪些节点可以并行？如何避免共享状态竞争？什么条件下跳过不必要的检索？
项目证据建议：保留节点耗时、结构化状态和分支原因，以对照实验说明延迟变化；不能在依赖未满足时提前评分。

## 工具调用与失败恢复
工具应定义清晰参数和返回结构。对模型输出进行 JSON 与字段校验，对外部服务错误使用有界重试或规则降级，避免无限循环。面试问题：如何处理工具超时、无效参数和不合法 JSON？重试预算耗尽后如何给出有用结果？
项目证据建议：提供故障注入案例，展示错误类别、节点状态和最终降级结果；日志中不记录 API Key 或完整简历。

## 可观测性与事实边界
节点日志应区分模型生成、规则计算和本地检索，记录耗时及降级原因。知识库提供方法参考，候选人能力只能依据简历；评分规则和模型建议应能分别追溯。面试问题：如何定位某次分析变差的节点？如何避免模型把 JD 要求改写成候选人已掌握的技能？
项目证据建议：保留输入摘要、来源 ID、分项得分和能力缺口，使用脱敏样例进行复现。
